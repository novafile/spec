## 0011.0 Summary

`std.Uri` is an RFC 3986 URI. Most URLs that programs handle today are WHATWG URLs: browsers, `fetch`, Node's `URL`, Rust's `url` crate and Go's `net/url` follow the URL Standard, not RFC 3986. The two disagree. `https://shop.example/?filter[size]=m|l` is a URL that every browser accepts and writes back unchanged, but it is not a URI. `HTTPS://Shop.Example:443` is a URI, but no URL parser writes it that way.

This proposal adds **`std.Url`**: a string that is the **serialization of a WHATWG URL**, which is exactly what a URL parser writes after reading a URL. It is the canonical spelling of a URL, in the sense of 0008.3.3. `std.Uri` stays as it is.

```
@import novafile.dev/std@0.2.0 as std

record Upstream:
  endpoint: std.Url
  callback: std.Uri          # where a strict RFC 3986 URI is wanted
```

## 0011.1 Motivation

1. **Bindings cannot map their URL type to `std.Uri`.** 0008.3.8 lets `novafile-derive` map `std.Uri` to `url::Url`, and says that a binding type that normalizes MUST NOT be used for serialization unless it round-trips the canonical spelling. `url::Url` does not round-trip `std.Uri`:
   - it writes characters a URI may not hold when its input had them: `Url::parse("https://a.example/?filter[a]=b|c")` writes the same string back, and `std.Uri` rejects it;
   - it rewrites URIs: `https://a.example` becomes `https://a.example/`, `HTTP://A.example:80/` becomes `http://a.example/`.

   The reference derive (nova#40) maps `url::Url` to `std.Uri` today and documents the first case as a boundary. A property test found it. With `std.Url`, a `Url` read from any document that validates writes back a string that validates, unchanged.
2. **Configuration holds URLs, not URIs.** Query strings with `[]`, `|` or `{}` come from real APIs (`filter[name]=…`, Elasticsearch, OData-like filters). A schema that uses `std.Uri` for them rejects valid configuration. The only alternative today is `string`, which checks nothing.
3. **One spelling per URL.** A URL type that accepted every string a URL parser accepts (whitespace, backslashes, `HTTP:`, Unicode hosts) would let `https://a.example/` and ` HTTPS://A.EXAMPLE ` be two different values of one type for one URL. 0008.3.3 rules that out for std: a std type accepts only the canonical spelling, so that equality (§2.12) means equality.

## 0011.2 Prior art

- **URL Standard (WHATWG).** Defines the parser, the serializer and the percent-encode sets this proposal derives its grammar from. It also defines a "valid URL string" authoring grammar. That grammar does not help here: it rejects `{`, `|`, `[` and `]` in queries just as RFC 3986 does, while every parser writes them.
- **Web Platform Tests**, `url/resources/urltestdata.json`. The shared conformance data of browser URL parsers: input, base and the expected `href`, which is a serialization.
- **JSON Schema** has `"format": "uri"` and `"iri"` (RFC 3986/3987) and no format for WHATWG URLs.
- **RFC 3986 and 3987.** The basis of `std.Uri`. An IRI (RFC 3987) admits non-ASCII but still not `{`, `|`, `[`, `]` in queries.

## 0011.3 Design

### 0011.3.1 Definition

`Url` is the set of strings that the URL serializer of the URL Standard can output, without the fragment-exclusion flag. Its pattern is generated by `std.py` from the grammar below, as `Uri` is generated from the RFC 3986 ABNF, and is about 3,800 characters of plain I-Regexp.

"Printable" means U+0021 to U+007E. Every percent-encode set of the URL Standard contains all code points above U+007E, so a serialization is ASCII. `%` is never encoded, so it may appear anywhere a path, query or fragment character may, followed by anything.

| Part | Grammar | Notes |
| --- | --- | --- |
| Special URL | `scheme "://" [userinfo "@"] host [":" port] ("/" segment)+ ["?" query] ["#" fragment]` | `scheme` is one of `http`, `https`, `ws`, `wss`, `ftp`. The path is never empty, so `https://a.example` is not a value; `https://a.example/` is |
| File URL | `"file://" [host] ("/" segment)+ ["?" query] ["#" fragment]` | No userinfo, no port. `file:///etc/hosts` has an empty host |
| Non-special URL with host | `scheme "://" [[userinfo "@"] opaque-host [":" port]] ("/" segment)* ["?" query] ["#" fragment]` | `scheme` is any scheme except the six special ones. The path may be empty: `foo://h` is a value |
| Non-special URL with path | `scheme ":" ("/" \| "/" segment+ ("/" segment)* \| "/." ("/" segment)+) ["?" query] ["#" fragment]` | `/.` is how the serializer marks a path that starts with an empty segment: `foo:/.//p` |
| Opaque URL | `scheme ":" [opaque-path] ["?" query] ["#" fragment]` | `mailto:a@b`, `data:text/plain,a b`, `urn:isbn:…`. The opaque path does not start with `/` |
| `scheme` | `[a-z][a-z0-9+.-]*` | Lowercase only; parsers lowercase it. "Not special" is spelled out as the complement of the six names, since I-Regexp has no lookahead |
| `userinfo` | `u+ [":" u+]` or `":" u+`, where `u` is printable minus ``"#<>?^`{}/:;=@[\]\|`` | The userinfo percent-encode set |
| `host` (special) | `d+` or `"[" [0-9a-f:]+ "]"`, where `d` is printable minus ` #/:<>?@[\]^\|`, `%` and `A`–`Z` | Domains after domain-to-ASCII, so lowercase and punycode. IPv4 addresses are domains by this grammar |
| `opaque-host` | `o+` or IPv6 as above, where `o` is printable minus ` #/:<>?@[\]^\|` | Hosts of non-special URLs keep their case and may contain `%` |
| `port` | `0`–`65535` without leading zeros, and not the scheme's default | Defaults: 80 (`http`, `ws`), 443 (`https`, `wss`), 21 (`ftp`). Non-special schemes have no default |
| `segment` | printable minus ``"#<>?^`{}/``; for special schemes also minus `\` | The path percent-encode set. Special schemes read `\` as `/` |
| `query` | printable minus `"#<>`; for special schemes also minus `'` | The query and special-query percent-encode sets. `?` may appear |
| `fragment` | printable minus ``"<>` `` | The fragment percent-encode set. `#` may appear |
| `opaque-path` | U+0020 to U+007E minus `?#` | The C0 control percent-encode set, so spaces stay |

### 0011.3.2 `Url` and `Uri`

Neither type contains the other:

| String | `std.Uri` | `std.Url` | Why |
| --- | --- | --- | --- |
| `https://a.example/?filter[a]=b\|c` | no | yes | RFC 3986 forbids `[`, `]` and `\|` in a query |
| `https://a.example/` | yes | yes | |
| `https://a.example` | yes | no | The serializer writes the empty path of a special URL as `/` |
| `HTTPS://a.example/` | yes | no | Schemes are lowercased |
| `https://a.example:443/` | yes | no | Default ports are dropped |
| `https://xn--bcher-kva.example/` | yes | yes | |
| `https://bücher.example/` | no | no | Hosts are written in ASCII |
| `mailto:a b@example.com` | no | yes | Opaque paths keep spaces |
| `urn:isbn:0451450523` | yes | yes | `std.Urn` is narrower still |

Use `Uri` when the value must be an RFC 3986 URI, for example because a non-WHATWG consumer will read it. Use `Url` when the value is handled by URL-Standard code, which is most HTTP clients and every browser.

### 0011.3.3 Known differences from the set of serializations

The grammar checks each part of a serialization on its own. It accepts a few strings that no serializer outputs, because ruling them out needs more than a regular grammar or would multiply the pattern's size:

- a host that ends in a number but is not a canonical IPv4 address (`http://0x7f.1/`; parsers write `http://127.0.0.1/`);
- an IPv6 address that is not in the serializer's compressed form (`[0:0::1]`);
- a domain that domain-to-ASCII would reject (`xn--zz`);
- `file://localhost/`, which parsers write as `file:///`;
- an opaque path that ends in a space.

None of these comes out of a URL parser, so a binding still round-trips. They only matter when a hand-written document should be rejected and is not. Each one SHOULD be listed in the type's documentation.

### 0011.3.4 Versioning and maintenance

- **std `0.2.0`.** Adding a type is a MINOR version (0008.3.6). std `0.1.0` is frozen and stays bundled. Its text moves unchanged to a versioned file, and `std.py` writes `0.2.0`.
- **The URL Standard is a living standard.** `std.Url` names the URL Standard as of a fixed commit, recorded in the type's documentation. A change of the standard that changes which strings are serializations is a new std version, classified by §6.5 like any other change: if a percent-encode set gains a character, fewer strings are values, which is breaking. A schema pinned to `std@0.2.0` keeps its meaning.
- **Generation.** `std.py` builds `Url` from the grammar of 0011.3.1. The complement of the special schemes and the port ranges without the default ports are generated, not written by hand.

### 0011.3.5 Interoperability

- **JSON Schema (§11.2).** Written as `"pattern"` plus `"x-nova-type": "novafile.dev/std.Url"`, like every std string type (0008.3.8). No `"format"`: `"uri"` and `"iri"` mean RFC 3986/3987, and JSON Schema has no format for WHATWG URLs. Reading `"format": "uri"` keeps producing `std.Uri`.
- **Protobuf.** `string`, as for every std string type.
- **Bindings (non-normative).** `novafile-derive` SHOULD map `url::Url` to `std.Url` once it bundles std `0.2.0`, in place of `std.Uri`. Types whose serialization is the URL serializer (`url::Url`, JavaScript `URL.href`) satisfy the round-trip requirement of 0008.3.8. Other URL types, such as Go's `net/url`, which is based on RFC 3986, need their own check before a binding maps them to `std.Url`.
- **Lints.** `std-hint` (0008.3.9) suggests `std.Url` rather than `std.Uri` for a field named `url` or `*_url`, and `std.Uri` for one named `uri`.

## 0011.4 What `Url` deliberately does not do

- **Accept what a URL parser accepts.** The parser accepts surrounding whitespace, tabs and newlines inside a URL, backslashes, uppercase schemes and Unicode hosts. That set is almost any string with a colon, and it holds many spellings of each URL. Resolution performs no conversions besides those of §6.3, so normalizing such input into `Url` is out of scope as well.
- **Check that a host exists, a scheme is registered or a port is open.** As for every std type (0008.3.3).
- **Base URLs.** `Url` is absolute. A relative-URL type would need the base, which the value does not carry.

## 0011.5 Evidence

The grammar was written as a Python generator of the pattern, the way `std.py` generates `Uri`, and checked as follows:

- **Web Platform Tests.** Every expected `href` in `url/resources/urltestdata.json` (634 serializations) matches.
- **Reject vectors.** `HTTP://a/`, `http://A/`, `http://a`, `http:foo`, `https://a/b\c`, `http://h:080/`, `http://h:65536/`, `https://a:443/`, `http://a/ b`, `http://a/é` and `http://a/?q#f g` are rejected. `foo://a:80/`, `mailto:x@y`, `file:///C:/x` and `data:text/plain,a b` are accepted.
- **Ports.** For each default port, the generated port pattern was compared with the intended set for every number from 0 to 69,999, and with `00`, `01` and `080`.
- **The reference engine.** `nvf validate` accepts the 3,772-character pattern within the schema budget (§12), accepts all 634 serializations and rejects the vectors above.
- **Rust `url` crate.** A property test parsed 4,000 generated inputs (special, non-special and opaque schemes; ASCII, Unicode, IPv4 and IPv6 hosts; ports; arbitrary Unicode paths), and every string `url::Url` wrote for them matched.

## 0011.6 Alternatives considered

- **`UrlRelaxed`.** The working name while this was discussed. `Url` is not a relaxed `Uri`: it rejects `https://a.example` and `HTTPS://…`, which `Uri` accepts. std names types after the standard they follow (`Uri`, `Urn`, `SemVer`, `E164`), and the URL Standard calls its object a URL.
- **Widen `Uri`.** That would change the meaning of `std.Uri` for every schema that bumps std, contrary to 0008.3.6, and `Uri` would no longer be RFC 3986.
- **A local pattern in each binding** (`string @pattern("[a-z][a-z0-9+.-]*:[ -~]*")` in the derive). Easy, but every binding would write its own, the schemas would not share an identity for code generators, and the loose pattern accepts many strings that are not serializations.
- **Map URL types to `string`.** Round-trips, checks nothing.

## 0011.7 Conformance cases

- `schema/std`: accept vectors for `Url` from the WPT `href` values at the pinned commit, and the reject vectors of 0011.5, each with a one-line reason.
- A case in which one value is a `Url` and not a `Uri`, and one the other way round, so that implementations cannot alias the two.

## 0011.8 Open questions

1. **Name.** `Url`, or something that names the standard (`WhatwgUrl`) so that `Url` and `Uri` side by side are not confused?
2. **Superset cases (0011.3.3).** Accept them, or generate the larger pattern that excludes the non-canonical IPv4 and IPv6 forms?
3. **Which commit of the URL Standard.** Pin to the commit at release time, or to a WPT commit, whose `href` values are the vectors?
4. **`file:` URLs** on Windows (`file:///C:/x`) are values. Should std say anything about drive letters, or leave that to `PortablePath` and 0008.4?
